# Archived: Postgres-era Alembic migration history

These 12 migration files are the full Alembic history as it existed
before the 2026-09-13 switch from PostgreSQL to MySQL (see
`docs/implementation-status.md`, "follow-up 8"). They are kept here for
historical reference only - they are NOT part of the live
`backend/migrations/versions/` chain anymore and must never be copied
back into it or run against the current (MySQL) database.

Why they couldn't just be replayed against MySQL: several contain
Postgres-only DDL/SQL that either fails outright or - worse - silently
does the wrong thing on MySQL. For example:

- `2019cf89921e_add_partial_unique_index_for_one_active_.py` and
  `b7e3d4f1a9c2_add_free_trial_plan_support.py` use
  `postgresql_where=...` on `op.create_index()` - a Postgres-dialect-only
  kwarg. On MySQL this doesn't error; it's just silently ignored,
  producing a FULL (non-partial) unique index instead - which would have
  permanently blocked any customer from having more than one
  subscription row ever, even cancelled/expired history.
- `1f06a0f4b4a6_add_target_plan_id_to_payment_.py` uses
  `UPDATE ... FROM ...`, Postgres's multi-table UPDATE syntax. MySQL
  needs `UPDATE ... JOIN ... SET ...` instead.

The live MySQL migration history starts fresh from
`2c58d7629015_initial_mysql_schema.py`, autogenerated directly from the
current SQLAlchemy models (which already include the MySQL-portable
generated-column fix for the two constraints above - see
`app/subscriptions/models.py`'s module docstring) and verified against a
real MySQL 8.0 instance.
